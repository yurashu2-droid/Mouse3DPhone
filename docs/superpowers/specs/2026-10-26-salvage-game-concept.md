# ゲーム企画案：ポケット・サルベージ

2026-10-26。ユーザーの「この仕組みを使ってゲームを作ってみて。企画段階でもよい」という依頼への提案。以下は提案仕様であり、実装済みのゲームやユーザー確定仕様ではない。

## ひとことで

スマホを宇宙船の小さな回収アームとして使い、壊れやすい部品を廃船から抜き取り、向きを合わせて回収ボックスへ収める、1プレイ2分の立体作業ゲーム。

手を前へ伸ばし、少しひねって、そっと引き抜く。「押すボタンが多い」より「手の動かし方を工夫すると上達する」を狙う。基本は座ったまま、机の前の小さな範囲で遊ぶ。

## なぜこの仕組みを使うか

現アプリは位置XYZ、姿勢、追跡状態、移動・掴み状態を送れる。単なる照準移動では位置計測の意味が薄いため、奥行きへの差し込みと姿勢合わせが同時に必要な作業をゲームにする。

新しいSDKを完成させることを先に条件にせず、ゲーム用受信側で既存v1を利用する。遊べるデモを通して、座標合わせや入力APIに何が必要か判断する。

## 比較した案

| 案 | この入力で楽しい部分 | 最初の試作で難しい部分 |
| --- | --- | --- |
| 部品回収（推奨） | 掴む、引く、ひねる、収める。今の2ボタンと対応する | 奥行きの見せ方と当たり判定の調整 |
| 異常探査 | スマホを伸ばして隙間や裏側を覗く | 手元映像を主役にすると配信遅延に依存する |
| 立体解錠 | 傾け方と位置で鍵穴を探る | 操作感より謎の説明や精密さが先に難しくなりやすい |

推奨案は担当AIによる選択。ユーザーが別の遊びを望めば変更する。

## 1プレイの流れ

1. 正面の作業台に3つの部品と、対応する回収ボックスを表示する。
2. 移動ボタンを押しながら、PC画面のアームを目的の部品へ近づける。掴める範囲に入ると部品の輪郭と距離表示が変わる。
3. 掴みボタンを押すと、その部品を固定。スマホを動かして引き抜き、回転させる。途中で別の部品へ選択が移らない。
4. 壁や障害物に接触すると、発光・短い効果音・耐久ゲージで知らせる。最初の版では耐久低下と得点減少に留め、部品を消して詰ませない。
5. ボックスに位置と向きを合わせるとガイドが緑になる。そこで指を離すと納品成功。合っていなければその場に浮いて置かれ、掴み直せる。
6. 3個納品、または2分経過でリザルト。納品数と残存耐久を中心に採点し、速さは小さなボーナスにする。

狙う瞬間は「狭くて抜けない → 少しひねったら通った → 傷つけず納品できた」。速く大きく振る操作は求めない。

## 最初のステージ

- 部品A：球形の電池。操作と距離感を覚える。向き合わせ不要。
- 部品B：細長いアンテナ。出口へ向けて回転させる必要がある。
- 部品C：L字の配管。持ち上げてひねると、障害物を越えられる。
- ボックスには半透明の完成姿勢を表示。静止した斜め視点と、部品直下の投影マーカーで奥行きを伝える。
- 操作練習は時間制限なし。本番とは別に再試行できる。

## 操作

| 入力 | ゲーム内の動作 |
| --- | --- |
| ポインター移動ボタンを押しながらスマホを動かす | アームだけ移動・回転 |
| 掴んで動かすボタンを押しながら動かす | 掴み候補を取得し、部品を移動・回転 |
| 両方を離す | アーム停止、部品をその場に置く。スマホを持ち直せる |
| 両方を押す | 掴みを優先。掴みだけ離すと部品を置いて移動を続ける |
| 感度スライダー | 移動と回転を個別調整。ゲーム側との二重倍率に注意する |

最初は既存アプリの文言のまま使える。ゲーム用の自動選択はPC側に新規実装する。Blender版の「active selected objectを掴む」をそのまま移植して、PCのマウス選択を要求しない。

掴み開始の立ち上がりで、範囲内の最寄りの候補を1つ選ぶ。候補なしで押した場合、押したまま近づくだけでは勝手に掴まず、押し直す。切断・再接続・追跡喪失では納品扱いにせず、アームと部品を固定してゲーム時間を一時停止する。復帰後は解放入力を確認してから再開し、自動で掴み直さない。

## PCとスマホの役割

最初の試作はPC画面にステージを描画し、スマホを入力専用にする。現在のPNGプレビュー5fpsに依存せず、まず手を動かす遊びが成立するか確かめる。

次の段階では、スマホをアーム先端の工具モニターにする。

- 距離、耐久、納品の位置・角度誤差は状態データで送り、スマホ側で描画する。状態更新は30回/秒を目標とする。
- アーム先端からの別視点映像は30fpsを目標とする別の技術検証。現状のPNG方式の設定変更だけで達成できるとは扱わない。圧縮動画の配信方式を検討し、遅延も測る。
- スマホ映像だけに当たり判定や必須情報を依存させず、PC側に判断基準を残す。
- iPhoneのカメラはARKit計測用に使い続ける。画面を見るためカメラを机や手で覆う持ち方は避け、手元だけを凝視する作りにしない。

双方向のゲーム状態通信、任意のボタン画面、30fps映像配信は現在未実装。初回試作の前提に混ぜない。

## 実装方針の案

PC版はUnityの小さな3Dゲームを第一候補とする（担当AIの提案。エディター環境の有無は未確認）。Blenderは既存ツールのまま保持し、ゲーム用実行環境にはしない。

構成は「v1受信・セッション管理」「ゲーム座標への変換と原点合わせ」「アームと掴み」「納品・接触・採点」に分ける。受信スレッドからゲームオブジェクトを直接操作せず、最新入力をゲーム更新で反映する。

現アプリのposition/rotationは感度と押下を適用した仮想ポインターの値で、生のARKitポーズではない。受信側で再び同じ感度処理を掛けない。Unityへの軸・回転変換はBlender用変換を流用せず、左右・上下・前後と各回転の小さな入力で確かめる。

開始時に原点と正面を合わせる短い手順を用意し、移動ボタンを離した持ち直しと原点リセットを区別する。物理モニターの向きが自動で分かるとは扱わない。

初版は掴んだ部品がアームへ一定の相対姿勢で追従する方式。置いた部品も無重力で静止する。物理ジョイントの揺れや跳ね返りは導入せず、接触によるダメージは連続接触で毎フレーム加算されないよう間隔を設ける。入力の遅れを「重い工具の演出」で隠す設計にはしない。

## 試作の範囲と順序

1. PC上でアームをキーボード・マウスから操作し、球1個を納品する。
2. 既存スマホアプリから受信し、原点合わせ、持ち直し、掴み・解放を確認する。
3. 回転が必要な部品2種、接触減点、2分のゲーム進行を足す。
4. ここまでで遊び心地を評価し、必要ならスマホの状態画面と映像配信へ進む。

最初は一人用・一ステージ・図形ベースの素材。ネット対戦、複数スマホ、アカウント、ランキング保存、本格SDK公開、精密物理は含めない。

## 試作の評価

- マウスで物体を事前選択しなくても、スマホだけで1個納品できる。
- 持ち直し、追跡喪失、再接続で部品が飛んだり勝手に納品されたりしない。
- 球では移動、アンテナでは回転を自然に使い分けられる。
- 奥行きや回転方向の混乱で失敗していないかを、遊んだ本人の感想で確かめる。
- 楽しさの仮説は未検証。「できた」だけで完成扱いせず、手で動かす意味が感じられるかを最初の判断にする。
